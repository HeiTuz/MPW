# 모드별 골격 + 채워진 예시 + 심화 규칙

이 문서의 한국어 골격·예시는 구조를 설명하기 위한 것이다. 실제 프롬프트의 언어는 [SKILL.md](../SKILL.md) §작성 모델이 바뀌어도 유지할 판단을 따른다. 기본 영어 지시문 안에서도 한국어 대사·카피·입력 원문·요청된 최종 산출물 언어는 보존한다.

골격은 내부 조립용이다. **요청한 결과와 필수 조건만 담은 짧은 완결본 하나**를 기본으로 내고, 상세판·역할 설명·평가표·작업 순서를 자동으로 추가하지 않는다. 긴 보고서나 넓은 실행 범위를 요청했어도 지시문 자체는 짧게 쓸 수 있다. 간결성 판정은 [image/surfaces.md](image/surfaces.md) §0-2가 정본이다.

## 축약어를 활용한 프롬프트 작성

MPW가 납품할 프롬프트에는 의도를 간결하게 전달하는 축약어·슬래시 태그를 사용할 수 있다. 사용자가 축약형을 요청했거나, 자연어로 길게 풀어 쓰는 것보다 짧으면서 뜻이 명확할 때 선택한다. 모든 프롬프트에 태그를 붙이거나 별도 축약 버전을 자동으로 만들 필요는 없다.

- 설명 방식은 `ELI5`, 요약은 `TL;DR`, 질의응답 형식은 `FAQ`, 구성은 `AIDA`처럼 표현할 수 있다. `/table`, `/tone:empathetic`, `/platform:YouTube` 같은 태그도 자연어 지시와 섞어 쓸 수 있다. 예시는 고정 명령어 목록이 아니며 대상과 문맥에 맞게 고른다.
- 축약하는 것은 반복 설명이다. 실제 작업·입력·보존 조건·출력 언어와 분량 등 결과를 결정하는 조건은 남긴다. 예를 들어 `/ELI5 + /table: Compare the two supplied plans in Korean. Preserve the exact prices and contract terms.`처럼 태그에 구체적인 과제를 이어 쓴다. 사용처 태그만으로 영상 길이 같은 세부 조건을 대신하지 않는다.
- 뜻이 모호한 약어·임의 태그는 같은 프롬프트 안에서 짧게 정의하거나 자연어로 쓴다. 수신자가 앞선 대화나 별도 약어 사전을 알아야만 실행할 수 있는 축약은 피한다. 정의와 태그를 합친 길이가 자연어보다 길어지면 자연어를 택한다.
- `/` 표기를 공식 기능이나 정확성·성능을 높이는 옵션으로 설명하지 않는다. 대상 도구의 실제 파라미터·스키마가 정해진 부분은 그 계약을 유지하고, 정확 문자열과 부분 수정 밖의 원문도 보존한다.

## 범용 조립 규칙

| 슬롯 | 포함 조건 | 생략 조건 |
|---|---|---|
| 역할 | 전문성·권한이 결과를 바꿀 때 | 일반 실행자로 충분할 때 |
| 목표·결과 | 항상: 끝난 상태를 판정해야 할 때 | 없음 |
| 입력·컨텍스트 | 답을 바꾸는 사실·경로·원문이 있을 때 | 장식 설명뿐일 때 |
| 완료 기준 | 제3자 판정·품질 증거가 필요할 때 | 단순 즉시 응답에 이미 명확할 때 |
| 제약·게이트 | 실제로 열려 있고 환경이 막지 않으며 발생 가능한 위험일 때 | 세 조건 중 하나라도 아닐 때 |
| 절차·도구 | 순서·도구 계약이 실패를 막을 때 | 방법을 과도하게 고정할 때 |
| 출력 형식 | 소비자가 형식·스키마를 요구할 때 | 평문이 더 명확할 때 |
| 검증·정지 | 실행·조사·반복 작업의 완료 또는 blocked 판정이 필요할 때 | 한 번의 저위험 응답일 때 |

**내용 없는 슬롯은 출력하지 않는다.** 이는 게이트 필요성 테스트의 슬롯판이다. 단순 저위험 과제는 헤딩 없는 1~3문장 명령형이 정답일 수 있다. 가독성이 인위적 압축보다 우선한다. 결론과 핵심 제약을 앞에 두고, 구조는 정보가 생길 때만 추가한다.

예시는 원하는 형식·분류 경계·실제 반복 실패를 설명할 때만 넣고, 규칙과 일치하는 최소 수를 쓴다. 단순 요청에 few-shot 묶음을 자동 추가하지 않으며, 내부 추론 모델에는 예시 없이 먼저 쓰고 출력 요구가 복잡할 때만 추가한다. 넣을 때는 서로 다른 입력 범위를 고르게 보여주고, 입력·기대 출력 쌍을 구분자나 id로 묶어 한눈에 읽고 고칠 수 있는 짧은 블록(불릿·YAML형·태그)으로 둔다. 예시가 지시 규칙과 어긋나면 예시가 이기므로 둘을 일치시킨다. 부정문은 실제 제외·보존 조건을 정확히 전달할 때 유지하고, 같은 금지를 여러 번 강조하지 않는다. 긍정문으로 바꾸면서 금지 범위를 넓히거나 의미를 바꾸지 않는다.

채워진 예시 (256자 실측):

```text
매주 금요일 18:00, ~/reports/weekly/의 신규 CSV(헤더 date,team,metric,value)를 팀별 요약표로 변환해 ~/reports/summary.md에 추가하라. 이미 처리한 파일은 건너뛴다(재실행 시 중복 행 0). 파싱 오류 파일은 삭제하지 말고 건너뛴 뒤 ~/logs/weekly.log에 사유를 남긴다. 완료 기준: 처리 파일 수·추가 행 수가 로그에 1줄 기록되고 summary.md 행 수가 로그 누적 수와 일치한다.
```

## 역할 슬롯 — 무엇으로 채우는가

역할은 평가 관점·권한·문체가 결과를 바꿀 때만 쓴다. "최고의 전문가" 같은 지위 장식 대신 필요한 기준이나 산출물 관례를 직접 명시한다.

**프롬프트 단어의 역할 5가지** — 범위 지정(어디서 찾을까?) / 목적 고정(무엇을 달성할까?) / 형식 강제(어떻게 출력할까?) / 오류 금지(무엇을 피할까?) / 행동 지정(어떻게 작업할까?). 각 역할에 맞는 단어를 선택하면 문제 공간이 축소되고 결과가 명확해진다.

**모호어 치환** — 이미 결과가 명확하면 미사여구만 지운다. 모호어가 필요한 요구를 대신하고 있을 때만 관찰 가능한 조건으로 바꾼다. 근거 없는 수량·평가표를 새로 만들지 않는다. 기본 목록은 §모호어 치환을 참고한다.

| 금지어 | 문제점 | 대안 |
|--------|--------|------|
| 대충 | 품질 하한선 붕괴 | 최소 품질 기준·체크리스트 명시 |
| 적당히 | 기대 결과가 불명확할 수 있음 | 주어진 목적에 맞는 기준을 쓰되 수량·길이를 임의로 정하지 않음 |

**역할이 필요할 때만** 대화·증거에서 평가 기준이나 산출물 관례를 고른다. 근거가 없으면 역할을 생략하고 결과를 직접 지시한다. 프레임워크 탐색·기준 열거를 새 과제로 덧붙이지 않는다.

**인물과 프레임워크의 구분** — 인물은 프레임워크의 이름으로만 쓰고, 인물의 목소리로 발화시키지 않는다.
- 금지: `당신은 Michael Porter입니다.`
- 허용: `Five Forces 축(공급자·구매자·대체재·신규진입·기존경쟁)으로 분해하고 각 축의 압력도를 평가하라.`
- 허용: `Porter의 Five Forces 프레임워크를 적용하라.` (관용적 소유격은 명칭이지 귀속이 아니다)

**예시** — 마케팅 전략 수립(214자 실측):

```text
마케팅 컨설턴트처럼 Kotler의 STP 프레임워크(세분화·타겟·포지셔닝)와 Five Forces 모델로 분석하라. 
[입력] 대상 산업·현재 고객군·기존 포지셔닝 
[출력] 세분화 축 3개 > 타겟 고객 프로필 > 포지셔닝 한 문장 > 기존 포지셔닝과의 차이점 3개 
[완료 기준] 각 포지셔닝이 다른 경쟁사와 구분되는 근거를 갖춰야 함. 근거 없는 형용사(혁신적, 독특한) 금지.
```


## 슬롯 자동 채움 — 빈칸은 묻기 전에 채운다

추론 순서는 대화 컨텍스트 → 언급된 저장소·파일 증거 → 아래의 저위험 기본값 → 결과나 하드라인을 바꾸는 빈칸만 질문 ≤3이다. 채운 값은 `가정:` 노트에 남긴다. 결과 자체가 없으면 슬롯 채움이 아니라 요구 구체화 경로다.

| 모드 | 비었을 때 채움 규칙 |
|---|---|
| GOAL | 마지막 언급 프로젝트가 하나로 명확할 때만 대상에 쓰고, 그렇지 않으면 행동 전에 대상을 식별·보고하게 한다. 완료 증거는 관련 테스트·명령 출력으로 둔다. |
| TEAM | 목표·범위는 대화에서 채운다. 독립 검증 표면이 둘 이상일 때만 그 경계에 맞춰 필요한 수의 레인으로 나누고, 검증은 기존 테스트나 측정기로 채운다. |
| CONTRACT | 결과는 대화와 산출물 관례에서 채운다. 완료 기준과 검증이 필요한지는 §CONTRACT를 따르고, 필요한 검증만 실제로 열거나 실행하는 최소 절차로 둔다. |
| BUSINESS | 직무·현실 제약·형식은 대화와 확인된 조직·도메인 관례에서 채우되, 근거 없는 지역·업계 관례는 기본값으로 만들지 않는다. 결과를 가르는 법령·기준 버전은 가정 또는 질문으로 처리한다. |
| MODEL | 대상이 미상이면 특정 모델에 의존하지 않는 목표·입력·핵심 조건으로 쓴다. 형식과 검증은 §MODEL의 포함 조건을 따른다. |
| 리서치 | 출처 유형·확인 날짜·반대 증거는 시점과 결론을 바꿀 때 추가한다. |
| 추출 | 아래 §추출의 소비자 스키마와 결측 규칙을 따른다. |

**추론 불가 슬롯 — 질문이 필요한 기준 (정본)**: 필수 입력이 없거나 충돌해 요청 결과·정확성·권한을 보존할 수 없을 때 묻는다. 대표 사례는 퇴고·델타의 기준 원문, 직접 확인해야 할 원본 자료, 정확한 카피·브랜드명, 실계정·서비스 식별자, 결과를 바꾸는 중요한 방향 선택이다. 나중에 자료를 넣어 실행할 프롬프트를 작성하는 요청이면 입력 위치와 역할을 명시해 완성한다. 지금 그 자료를 읽은 것처럼 말하거나 작성에 불필요한 업로드를 요구하지 않는다.

## 수신자·채널 적응

수신자·채널은 사용자가 지정한 대상과 현재 전달 환경에서 확인한다. 미지정이면 복사 가능한 일반 텍스트로 작성하며 메신저 상한·파일 접근·도구 권한을 가정하지 않는다. 파일·도구 없는 대화 UI에는 필요한 자료를 인라인하고, API 시스템 프롬프트에는 입력 위치·불확실 시 행동을 명시한다. 사람 팀원에게는 사람용 제목·불릿으로 바꾸되 결과·경계·검증은 유지한다. 채널이 달라져도 길이 상한은 전달 채널·타깃 엔진·기계 계약 세 층 중 가장 좁은 것이 구속한다 — 판정 절차와 값의 정본은 [image/surfaces.md](image/surfaces.md) §0-1이다. 어느 표면이든 다른 파일시스템에는 경로 참조 대신 자기완결로 쓴다.

## 메시지 역할과 배치 — API·시스템 프롬프트

API나 앱에 들어가는 프롬프트는 한 덩어리 텍스트가 아니라 **역할이 다른 메시지의 조합**으로 납품한다. 공식 근거·확인일은 [model-playbooks.md](model-playbooks.md) §호환 노트의 dated note에 둔다.

- **역할 분리.** 정체성·톤·규칙·예시처럼 요청마다 변하지 않는 것은 시스템/개발자 지시(`instructions` 또는 developer 메시지)에, 이번 과제의 입력·자료·질문은 user 메시지에 둔다. 개발자 지시는 함수 정의, user 메시지는 인자에 해당한다. 상위 지시가 하위 입력보다 우선하므로, 자료 안의 문장을 지시로 승격하지 말라는 규칙과 불확실할 때의 행동은 상위 지시에 적는다. 파일·도구 없는 대화 UI에 붙여넣는 프롬프트는 이 분리를 한 블록 안의 구획으로 옮긴다.
- **구획과 순서.** 구조가 필요할 만큼 내용이 있을 때만 정체성 → 지시 → 예시 → 컨텍스트 순으로 두고, 요청마다 바뀌는 자료는 맨 뒤에 둔다. 위계는 Markdown 헤딩·목록으로, 자료의 시작과 끝은 XML 태그로 표시하고 출처·id 같은 메타데이터는 태그 속성에 둔다. 긴 자료 뒤에 실제 질문을 두는 규칙([model-playbooks.md](model-playbooks.md) §공통 적응 규칙)과 같은 원리다. 짧은 과제에 빈 구획을 만들지 않는다.
- **고정 부분은 앞, 가변 부분은 뒤.** 반복 호출되는 프롬프트는 안정된 지시·도구 정의·참고 자료를 접두부로 고정하고, 타임스탬프·사용자별 값·이번 요청 자료는 뒤쪽이나 이후 메시지에 둔다. 대화는 이전 턴을 다시 쓰지 않고 뒤에 덧붙이며, 도구는 정의를 유지한 채 허용 여부만 바꾼다. 이렇게 두면 프롬프트 캐시가 접두부를 재사용해 비용·지연이 준다. 캐시 최소 길이·쓰기 비용·브레이크포인트 같은 값은 런타임 계약이며 dated note에서만 인용한다.
- **코드로 관리한다.** 앱용 프롬프트는 기능 옆의 작은 모듈로 납품하고, 가변 값은 문자열 치환이 아니라 타입 있는 인자·검증된 입력 객체로 받는다. 생성한 지시·입력을 API에 직접 전달하며, 원격 저장형 재사용 프롬프트 객체(프롬프트 ID·버전 참조)는 새로 만들지 않는다. 프로덕션 호출은 특정 모델 스냅샷에 고정하고, 프롬프트 변경마다 대표 fixture·평가 케이스를 배포 절차에서 돌리며 git 이력·리뷰·릴리스 태그·기능 플래그로 비교·롤백한다. 사용자가 이 운영 방식을 요청하지 않았으면 프롬프트 본문만 내고, 통합 방식은 필요한 한 줄 가정으로 남긴다.

## 위임 계약 6요소

실행 작업을 위임할 때 아래를 점검하되, 결과를 바꾸는 요소만 문장에 남긴다. 단순 즉시 응답에 별도 승인·중단·검증 절차를 억지로 넣지 않는다.

| 요소 | 계약이 답해야 할 질문 |
|---|---|
| 결과 명세 | 끝난 상태는 무엇인가? |
| Definition of Done | 무엇을 보면 완료라고 판정하는가? |
| 자율성 3단 | 혼자 결정 / 보고 후 진행 / 절대 금지는 무엇인가? |
| 하드라인 | 범위에서 실제로 지켜야 할 경계는 무엇인가? |
| 검증 계약 | 완료 전에 확인할 결과와 증거는 무엇인가? |
| 에스컬레이션 | 해결을 시도해도 남는 막힘을 언제, 어떻게 보고하는가? |

이미 허가된 실행 범위에서는 필요한 구현·동작 확인·문제 수정을 끝낸 상태를 완료로 정한다. 실제 승인 경계가 없으면 첫 구현 뒤 검토 대기를 기본 종료점으로 넣지 않는다.

## GOAL — 자율 에이전트 goal 지시문

**필수 코어**: 결과, 완료 기준, 최종 보고, 막혔을 때. **조건부 확장**: 게이트·컨텍스트·우선순위는 실제 정보가 있을 때만 추가한다. 판정자가 앞부분과 최종 보고를 본다고 가정해 핵심을 앞배치한다.

```text
<결과 — 끝난 상태>

완료 기준:
- <경로·명령 출력·개수 등 판정 증거>

최종 보고: 변경한 것 / 검증한 것(명령+결과) / 안 한 것과 이유.
막히면: <기준> → 시도한 것/막힌 지점/필요한 것 형식으로 종료.
```

조사·구현·검증이 하나의 완료 기준으로 이어지면 같은 goal에 둔다. 독립 산출물, 별도 실행 시점, 실제 승인 대기로 실행 경계가 갈릴 때만 나눈다. 추가 승인이 필요한 행동은 증거와 승인 요청문 준비까지 수행하고, 이미 승인된 후속 작업은 같은 goal에서 완료한다.

채워진 예시 (215자 실측):

```text
~/src/acme-api 의 플래키 결제 테스트 2건이 원인 수정으로 연속 20회 통과하는 상태.

완료 기준:
- pytest tests/payment --count 20 연속 통과 로그
- 원인과 수정 diff 요약 1문단

최종 보고: 변경한 것 / 검증한 것(명령+결과) / 안 한 것과 이유.
막히면: 2시간 내 재현 불가 → 시도한 것/막힌 지점/필요한 것 형식으로 종료.
```

## TEAM — 멀티에이전트 킥오프

**필수 코어**: 목표, 범위·비목표, 레인, 검증, 산출물. **조건부 확장**: 컨텍스트·경계·상세자료는 워커 판정을 바꿀 때만 넣는다. 같은 acceptance를 공유하는 구현과 검증은 같은 레인에 둔다.

```text
목표: <구체적 결과 하나>
범위: <대상> / 비목표: <명시적 제외>
작업 방식: <독립 검증 표면별 레인과 조율 규칙>
검증: <명령·시나리오·증거>
산출물: <파일·패치·보고서>
```

채워진 예시 (255자 실측):

```text
목표: acme-web 초기 로드 p95 를 3.2s에서 1.5s 이하로 내리는 패치 완성.
범위: ~/src/acme-web 로컬 브랜치 / 비목표: 디자인 변경, 백엔드 수정.
작업 방식: prime이 병목 인벤토리 확정 후 번들·폰트 레인을 분배하고, 같은 acceptance의 구현+검증은 한 레인에 둔다.
검증: scripts/perf.sh 3회 중앙값 p95 ≤ 1.5s, npm test 전체 통과.
산출물: 로컬 브랜치 + 수치 비교 보고서.
```

### TEAM 역할·분해

역할·capability·분해·join·blocker·증거 규칙의 정본은 [model-playbooks.md](model-playbooks.md)다. 아래는 TEAM 골격의 `작업 방식` 필드에 넣는 압축 블록이며, 호출 접두어와 실제 모델 선택은 [adapters.md](adapters.md)에서 채운다.

```text
작업 방식: prime이 최상위 결과 목록과 acceptance를 확정한 뒤, 검증 표면이 독립적인 slice만 worker에 배정한다. 같은 acceptance를 공유하는 구현+테스트는 한 레인에 둔다. worker는 target/scope/non-goals/acceptance 안에서 실행하고, prime은 실제 배정한 레인과 요청된 검토 결과를 받은 뒤 최종 frozen artifact를 통합 검증한다. human-only blocker만 질문한다.
```

## CONTRACT — 작업지시·시스템 프롬프트·자동화 잡

**필수 코어**: 결과. 완료 상태가 결과 문장만으로 분명하지 않을 때 완료 기준을 추가한다. **조건부 확장**: 검증은 실행 결과·사실·기계 형식을 확인해야 할 때 필요한 범위로 정하고, 자료·자율성·게이트·막힘 규칙·컨텍스트는 필요할 때만 붙인다. 자동화 잡은 멱등성과 오류 기록을 추가하고, 시스템 프롬프트는 DoD를 응답 품질 기준으로 바꾼다. API·앱에 통합되는 시스템 프롬프트는 §메시지 역할과 배치에 따라 상위 지시와 요청별 입력을 나눠 납품한다.

```text
## 결과
<끝난 상태>

## 완료 기준 (결과 문장만으로 불분명할 때)
- <판정 가능한 증거>

## 검증 (필요할 때)
- <완료 판정에 필요한 실행 또는 대조 절차>
```

## BUSINESS — 직무 업무 프롬프트

결과를 직접 지시하고, 형식·근거·검증은 정확한 납품에 필요할 때만 붙인다. 역할·작업 단계·예외 목록은 난이도만으로 늘리지 않는다. 채워진 예시는 비표준 형식의 오해를 막을 때만 추가한다.

채워진 예시 (138자 실측):

```text
개인 카페의 메뉴별 원가율을 계산하라. 표는 메뉴 | 판매가 | 재료비 | 원가율 | 판정 | 대안으로 출력하고, 제공되지 않은 값은 미확인으로 표시한다. 원가율 40% 초과 메뉴마다 가격 또는 레시피 대안 하나를 제시한 뒤 계산 근거를 대조하라.
```

### BUSINESS 산출물 축 사전 — 표형·전환·검색

직무 요청이 아래 산출물 유형일 때만 읽는 조건부 사전이다. 골격이 아니라 **결과를 가르는 축**의 목록이며, 내용 없는 축은 출력하지 않는다. 직무 공통으로 반복되는 축은 타겟 · 기간 · 채널 · KPI · 제약이고, 빈 축은 §슬롯 자동 채움 규칙으로 채운다.

#### 표형 산출물 — 캘린더·레지스터·백로그류

모호어 치환표의 "잘 정리해"가 표 요청으로 들어왔을 때, 게으른 나열이 통과하지 못하게 거는 장치 네 가지다. 공통 코어 "비자명 형식엔 채워진 예시" 규칙의 표 특수화다.

| 장치 | 규칙 |
|---|---|
| 컬럼 스키마 | 컬럼명을 열거해 잠근다. 예: 콘텐츠 캘린더 `week, date_or_day, platform, format, theme, hook, key_message, cta, production_notes` / KPI 표 `platform, primary_kpi, definition, measurement_tool, reporting_frequency` |
| 수량·커버리지 | 사용자가 지정한 개수·분류는 보존한다. 미지정이면 근거 있는 항목만 요구하며, 예시 수량을 최소 개수로 강제하지 않는다 |
| 실행 필드 | 실행·추적이 목적이고 담당자·기한·상태가 결과를 가를 때만 `owner`, `due`, `status`를 요구한다. 값이 없으면 필드를 지어내지 않고 생략하거나 미정으로 둔다 |
| 발견→액션 결합 | 의사결정·실행을 요구하는 분석에만 각 발견(finding)에 필요한 액션을 매핑한다. 진단·현황 보고는 액션 없이 끝낼 수 있으며, 액션을 요구할 때만 무엇을/왜/어떻게/측정 중 필요한 항목을 둔다 |

근거 없는 셀은 지어내지 말고 `미확인`으로 표기한다. 사용자가 추정이나 모델링을 허용한 경우에만 `추정`으로 표시하고 가정·근거를 함께 쓴다.

#### 전환 카피 — 상세페이지·프로모션·리마케팅

| 축 | 규칙 |
|---|---|
| 헤드라인 | 차별 가치 1문장. 미사여구가 아니라 구매자가 얻는 결과로 쓴다 |
| 혜택 | 기능 나열 대신 기능→혜택 환원을 요구한다 — "무엇이 있다"가 아니라 "그래서 무엇이 된다" |
| 증거 | 제공된 검증 가능 증거만: 실제 리뷰·수치·인증. 없는 증거를 지어내는 것은 하드라인 |
| 위험 제거 | 보장·교환·배송·결제 단계를 명시해 구매 장벽을 걷는다 |
| 긴급성 | 실제 사실(실제 마감일·실제 재고)일 때만 쓴다. 허위 희소성 연출은 하드라인 — 입력에 사실이 없으면 이 축을 생략한다 |
| CTA | 행동 동사 1개 + 다음 단계 1개. CTA가 둘이면 같은 축에 권한자가 둘인 것이다([prompt-graph.md](prompt-graph.md) §4) |

상세페이지 기본 순서는 헤드라인 → 혜택 → 증거 → 가격·위험 제거 → CTA다. 리마케팅 메시지는 담긴 상품 목록·금액 확인 → 인센티브 → 결제 마찰 제거 세 축이 결과를 가른다. 프로모션은 조건(대상·제외·기한)의 투명한 명시까지가 완료 기준이다.

#### 검색·응답엔진 콘텐츠 — 블로그·가이드류

| 축 | 규칙 |
|---|---|
| 키워드 계층 | primary(제목·H1) / 연관·의미 확장(H2·H3) / 구체 검색 문구(본문) / question(FAQ 문항)을 필요에 따라 분리하고, 한 계층을 다른 위치에 억지 반복시키지 않는다 |
| answer-first | 핵심 질문의 직답을 도입부에 선행시키고 상세를 뒤에 둔다. FAQ 답변도 결론형 직답 |
| 구조 | H2는 primary 축, H3는 연관 축, 세부는 불릿. FAQ 섹션은 question 키워드로 구성한다 |
| 메타 길이 | 제목·디스크립션은 검색 결과 표시 폭이 자르는 관례 상한을 따른다 — 라틴 문자 기준 제목 50~60자·디스크립션 150~160자로 회자되며, 전각인 한글은 같은 폭에 문자 수가 절반 수준이다. 보장이 아니라 표시 관례로 다룬다 |
| 구조화 데이터 | 웹 게시가 확정된 요청에만 FAQ·Article·HowTo류 구조화 마크업 생성을 지시한다. 채널 미정이면 생략 |

플랫폼별 인용률 증감 수치("통계를 넣으면 +N%"류)는 근거 미실측 주장이므로 프롬프트에 싣지 않는다.

## MODEL — 퇴고·델타·리서치·추출·체인

**필수 코어**: 대상 또는 원문, 원하는 결과. **조건부 확장**: 결과 형식은 소비자가 요구할 때, 별도 검증은 실행 결과·사실·기계 형식을 확인해야 할 때 추가한다. 역할·도구·증거 규칙은 대상 작업이 요구할 때만 쓴다. 검토만 요청하면 문제·근거·수정 방향을 보고하고, 퇴고는 수정본과 필요한 실제 변경 노트를 낸다. 델타는 지정 축만 바꾸고 나머지 문구·권한·수량·출력 조건을 보존한다. 기준 원문은 대화에서 먼저 찾고, 없으면 요청한다.

### 리서치

**필수 코어**: 조사 질문, 출처·날짜가 있는 결론 형식. 검증은 결론을 뒷받침하는 사실·출처 대조로 구체화하며 별도 반복 검사 절차를 자동으로 붙이지 않는다. **조건부 확장**: 반대 증거·불확실성은 결론을 바꿀 수 있을 때 추가한다. 공식·1차 자료를 최신 블로그나 기사보다 우선하며 상충은 숨기지 않는다.

채워진 예시 (221자 실측):

```text
## 결과
국내 클라우드 백업 3사의 요금제 비교 보고서를 작성한다.

## 완료 기준
- 각 사의 요금제명·월 요금·용량·초과 과금을 표 하나에 정리
- 모든 값에 출처 URL과 확인 날짜를 붙이고 확인 못 한 값은 "미확인"으로 표시
- 상충 수치는 병기하고 공식 가격 페이지를 우선

## 막혔을 때
가격 페이지 접근이 두 번 실패하면 해당 사를 "확인 불가"로 표기하고 나머지를 진행한다.
```

팩트체크·판정 등급·출처 신뢰도·증거 분류 축은 [research.md](research.md)가 정본이다.

### 추출

**필수 코어**: 입력, 스키마, 원문 밖 추측 금지. **조건부 확장**: 중복 규칙·정규화는 소비자가 요구할 때만 넣는다.

스키마는 실제 소비자 계약이 정본이다. 네이티브 구조화 응답이나 도구 인자 스키마가 이미 전달되면 형식 설명용 스키마·JSON 예시를 본문에 반복하지 않는다. 응답 형식과 도구 호출을 구분하고, 본문에는 입력·근거 제한·분류 경계처럼 스키마만으로 전달되지 않는 조건을 둔다. 네이티브 기능이 없을 때만 정확한 스키마를 한 번 포함한다.

결측값은 해당 필드가 허용할 때만 `null`로 둔다. 생략 가능한 필드의 누락과 필수 필드의 null 허용은 별개다. 필수·non-null 값이 없으면 소비자가 정한 오류 경로를 따르고, 그 경로도 없으면 불일치를 알린다. 값을 지어내거나 타입을 바꿔 통과시키지 않는다. 형식 통과와 원문 대비 값 검증을 구분한다. [OpenAI 구조화 출력](https://developers.openai.com/api/docs/guides/structured-outputs#all-fields-must-be-required), [Gemini 구조화 출력](https://ai.google.dev/gemini-api/docs/structured-output#best-practices) 확인: 2026-09-05.

네이티브 스키마 기능이 없는 대화의 예시 (129자 실측):

```text
아래 텍스트를 JSON 객체로 추출하라.
스키마: {"업체명": str|null, "연락처": str|null, "주소": str|null}
원문에 없는 값은 null로 두고 다른 필드·설명·추측은 추가하지 마라.
텍스트: <원문>
```

### 체인

단계별 블록을 분리하고, 앞 단계의 산출 형식과 다음 단계의 입력이 같은 스키마임을 예시로 대조한다. 다음 단계가 요구하는 입력 계약을 대조하되, 단계마다 별도 검증 문장을 자동으로 붙이지 않는다.

## DESIGN 오버레이

실행 모드의 코어 위에만 겹친다. 이미지 DESIGN 레인의 필수 요소는 [image/lanes.md](image/lanes.md) §레인 게이트 카드가 정본이고, 이 절은 실행 모드 코어와의 결합 및 조건부 확장만 소유한다. **조건부 확장**: 시그니처·마이크로 인터랙션·기술 제약은 구현 결과를 바꿀 때만 둔다. 방향은 제품 맥락에서 하나를 가정으로 선언하고, 막연한 미사어 대신 표면·서체·간격·상호작용처럼 관찰 가능한 속성으로 쓴다. 기존 UI 수리는 결함을 한 문장으로 지목하고 최소 수정부터 수행한다.

채워진 예시 (198자 실측):

```text
## 디자인 방향
- 방향: raw terminal — 종이 같은 오프화이트와 잉크 블랙, 정보 밀도는 높고 계층은 분명하게.
- 시그니처: 가로 시간선이 섹션 구분을 맡는다.
- 하드 제약: 기존 프레임워크와 접근성 대비를 지킨다.

## 완료 기준
- 구현 전 시각 테제 3줄을 정하고 결과와 대조
- 데스크톱과 375px에서 긴 문자열의 넘침을 확인
```

## 모호어 치환

| 모호어 | 치환 방향 |
|---|---|
| 적절히 처리해 | 실패 기준과 재시도·기록 행동을 쓴다 |
| 잘 정리해 | 사용 목적에 맞는 분류·순서를 명시한다. 개수·길이는 요청이나 소비자 계약에 있을 때만 고정한다 |
| 최대한 자세히/빨리 | 필요한 근거·우선순위를 명시한다. 시간 제한은 실제 제약이 있을 때만 쓴다 |
| 필요하면 | 조건 C가 참이면 X로 바꾼다 |
| 등, 기타, 알아서 | 포함 범위나 실행자가 선택할 기준을 분명히 한다. 열린 목록을 임의로 닫지 않는다 |
| 중요한 것 위주로 | 판단 기준을 쓴다 |
| 완벽하게/깔끔하게/고급스럽게 | 판정 가능한 기준과 증거로 바꾼다 |
| nicely / properly / in detail | 영어 표현도 같은 기준으로 필요한 요구를 구체화한다. 인용문·정확 카피는 보존한다 |

## 워크플로우

1. **분류** — 모드 선택. 빈 슬롯은 §슬롯 자동 채움으로 채우고 `가정:`에 기록한다.
2. **결과 명세** — 끝난 상태 1~2문장과 자료 인벤토리. 언급된 경로는 실제로 읽고 사실을 지어내지 않는다.
3. **계약층** — 결과만으로 완료 판정이 불분명할 때 완료 기준을 추가한다. 자율성·게이트·검증·에스컬레이션은 해당 작업에 필요한 것만 붙인다.
4. **구조층** — [prompt-graph.md](prompt-graph.md) §8의 적용 신호가 있을 때 §3의 조립 절차를 쓴다. 단순하고 충돌 없는 요청은 바로 작성한다. `origin`·`status`는 내부 provenance로만 쓰고, 비자명·비표준 형식에만 채워진 예시 1개를 둔다.
5. **표면층** — 대상 수신자·도구에 맞춘다. 모델 적응·역할 배분이 필요할 때 [model-playbooks.md](model-playbooks.md)를 읽고, 나머지는 §수신자·채널 적응으로 충분하다.
6. **감량** — 모호어 치환, 제약 모순 해소, 방법 문장 다이어트("지우면 실행자가 틀리는가?").
7. **길이 게이트** — 실측이 필요한 조건·단위·상한은 [image/surfaces.md](image/surfaces.md) §0-1을 따른다.
8. **드라이런** — 비자명한 형식·실행 계약일 때만 현실 입력과 엣지 사례로 머릿속 실행해 구멍을 수정한 뒤 출력한다.

## 후속 선택

**이 턴이 실제로 프롬프트 블록을 냈고 후속 선택이 유용할 때만** 블록 밖에 평문 `다음:` 메뉴를 붙인다. 검토만 한 턴·스킬 수정·설치·검증 보고에는 붙이지 않는다. 사용자 지정 출력 형식이 메뉴를 허용하지 않거나, 다음 행동을 이미 지시했거나, 사람에게 응답하지 않는 자율 루프 안에서 호출됐거나 기계 핸드오프(S1)이면 생략한다. 사람이 GOAL 프롬프트를 작성해 달라고 한 대화에서도 메뉴가 결과를 부풀리면 생략할 수 있다. 대화형 선택 도구로 응답을 대기시키지 않는다.

1번은 아래 문구로 고정한다.

```text
다음:
1. 자동 개선 — 확인된 결함만 수정하고 의도·범위·조건은 보존
```

**자동 개선은 요청 한 번에 1회만** 수행한다. [SKILL.md](../SKILL.md) §출력 게이트에서 확인된 결함만 고친다. 모호어를 판정 가능한 조건으로 바꾸고, 저신호 어휘·중복·장식을 줄인다. 목표·범위·권한·모델·구도·소품·조명·컬러 등 결과를 바꾸는 축을 새로 고르지 않는다. 결함이 없으면 `개선할 지점 없음`이라고 알리고 원본을 유지한다. 수정본을 반환한 턴에도 사용자가 후속 선택을 요청했을 때만 메뉴를 붙이며, 사용자가 고르기 전 다음 개선을 자동 실행하지 않는다.

2번 이후에는 **지금 산출물에 적용할 구체적 연산만 최대 3개** 붙인다. 후보는 지정 축의 MODEL-델타, 다른 모델·플랫폼으로 재컴파일, 컷 분리, 레인 전환, 표면 파라미터 조정, 체인의 다음 단계다. 결과가 어떻게 달라지는지 적을 수 없는 `더 자세히`·`다른 스타일로` 같은 항목은 빼며, 후보가 없으면 1번만 둔다.

IMAGE 실행 핸드오프는 [adapters.md](adapters.md) §이미지 생성 실행 옵션의 조건을 만족할 때 마지막 번호에 붙인다. 실행 도구는 실제 설치와 현재 사용 가능 여부로 판단한다.

## 안티패턴

단계 마이크로매니징(→ 결과와 필요한 완료 조건만 계약) / 장문 인라인 덤프(→ 경로 참조) / 전면 read-only 과잉 차단(→ 좁은 게이트+대체 행동) / 환경 훅이 이미 막는 행동의 이중 게이트(→ 필요성 테스트로 제거) / 질문 반사(→ 추론·기본값 먼저, 질문은 추론 불가 슬롯만) / "알아서" 위임(→ 자율성 3단 경계) / 하나의 비대 goal(→ 분할) / 예시-규칙 충돌 방치(→ 대조 감사) / 무대 지정 어휘("최고 수준으로" → 수치·구체 기준) / 패딩용 문서.

## 보강 루프

결과·모드·레인이 유지되고 한 축만 바뀌면 패치한다. 하나라도 바뀌거나 계약 요소 여러 개가 흔들리면 재작성한다. 압축은 장식 → 중복 → 방법 설명 순으로 줄이며 실제 완료 기준·권한 경계·검증 계약은 보존한다. 실패하면 지시문·입력·도구·환경 중 원인을 먼저 구분한다. 지시문이 원인일 때만 관련 문구를 수정하거나 불필요한 규칙을 삭제한다. 원인이 확인되지 않으면 지시를 늘리지 않는다. 수정 뒤에는 변경한 조건과 그 영향만 대조한다.
