# 텍스트 브랜치 공통 규칙 + 골격

모든 텍스트 브랜치(TEXT-SIMPLE 제외 — 커널만으로 작성)가 읽는 공통 규칙이다. 모드별 골격은 같은 디렉터리의 파일을 따른다.

이 문서의 한국어 골격·예시는 구조를 설명하기 위한 것이다. 실제 프롬프트의 언어는 §수신자·채널 적응의 **프롬프트 언어 결정** 규칙을 따른다. 지시문 언어와 무관하게 한국어 대사·카피·입력 원문·요청된 최종 산출물 언어는 보존한다.

골격은 내부 조립용이다. **요청한 결과와 필수 조건만 담은 짧은 완결본 하나**를 기본으로 내고, 상세판·역할 설명·평가표·작업 순서를 자동으로 추가하지 않는다. 긴 보고서나 넓은 실행 범위를 요청했어도 지시문 자체는 짧게 쓸 수 있다. 간결성 판정은 [image/surfaces.md](../image/surfaces.md) §0-2가 정본이다.

## 축약어를 활용한 프롬프트 작성

MPW가 납품할 프롬프트에는 의도를 간결하게 전달하는 축약어·슬래시 태그를 사용할 수 있다. 사용자가 축약형을 요청했거나, 자연어로 길게 풀어 쓰는 것보다 짧으면서 뜻이 명확할 때 선택한다. 모든 프롬프트에 태그를 붙이거나 별도 축약 버전을 자동으로 만들 필요는 없다.

- 설명 방식은 `ELI5`, 요약은 `TL;DR`, 질의응답 형식은 `FAQ`, 구성은 `AIDA`처럼 표현할 수 있다. `/table`, `/tone:empathetic`, `/platform:YouTube` 같은 태그도 자연어 지시와 섞어 쓸 수 있다. 예시는 고정 명령어 목록이 아니며 대상과 문맥에 맞게 고른다.
- 축약하는 것은 반복 설명이다. 실제 작업·입력·보존 조건·출력 언어와 분량 등 결과를 결정하는 조건은 남긴다. 예를 들어 `/ELI5 + /table: Compare the two supplied plans in Korean. Preserve the exact prices and contract terms.`처럼 태그에 구체적인 과제를 이어 쓴다. 사용처 태그만으로 영상 길이 같은 세부 조건을 대신하지 않는다.
- 뜻이 모호한 약어·임의 태그는 같은 프롬프트 안에서 짧게 정의하거나 자연어로 쓴다. 수신자가 앞선 대화나 별도 약어 사전을 알아야만 실행할 수 있는 축약은 피한다. 정의와 태그를 합친 길이가 자연어보다 길어지면 자연어를 택한다.
- `/` 표기를 공식 기능이나 정확성·성능을 높이는 옵션으로 설명하지 않는다. 대상 도구의 실제 파라미터·스키마가 정해진 부분은 그 계약을 유지하고, 정확 문자열과 부분 수정 밖의 원문도 보존한다.
## 범용 조립 규칙

| 슬롯 | 포함 조건 | 생략 조건 |
|---|---|---|
| 역할 | 전문성·권한이 결과를 바꿀 때 | 일반 실행자로 충분할 때 |
| 목표·결과 | 항상: 끝난 상태를 판정해야 할 때 | 없음 |
| 입력·컨텍스트 | 답을 바꾸는 사실·경로·원문이 있을 때 | 장식 설명뿐일 때 |
| 완료 기준 | 제3자 판정·품질 증거가 필요할 때 | 단순 즉시 응답에 이미 명확할 때 |
| 제약·게이트 | 실제로 열려 있고 환경이 막지 않으며 발생 가능한 위험일 때 | 세 조건 중 하나라도 아닐 때 |
| 절차·도구 | 순서·도구 계약이 실패를 막을 때 | 방법을 과도하게 고정할 때 |
| 출력 형식 | 소비자가 형식·스키마를 요구할 때 | 평문이 더 명확할 때 |
| 검증·정지 | 실행·조사·반복 작업의 완료 또는 blocked 판정이 필요할 때 | 한 번의 저위험 응답일 때 |

**내용 없는 슬롯은 출력하지 않는다.** 이는 게이트 필요성 테스트의 슬롯판이다. 단순 저위험 과제는 헤딩 없는 1~3문장 명령형이 정답일 수 있다. 가독성이 인위적 압축보다 우선한다. 결론과 핵심 제약을 앞에 두고, 구조는 정보가 생길 때만 추가한다.

예시는 원하는 형식·분류 경계·실제 반복 실패를 설명할 때만 넣고, 규칙과 일치하는 최소 수를 쓴다. 단순 요청에 few-shot 묶음을 자동 추가하지 않으며, 내부 추론 모델에는 예시 없이 먼저 쓰고 출력 요구가 복잡할 때만 추가한다. 넣을 때는 서로 다른 입력 범위를 고르게 보여주고, 입력·기대 출력 쌍을 구분자나 id로 묶어 한눈에 읽고 고칠 수 있는 짧은 블록(불릿·YAML형·태그)으로 둔다. 예시가 지시 규칙과 어긋나면 예시가 이기므로 둘을 일치시킨다. 부정문은 실제 제외·보존 조건을 정확히 전달할 때 유지하고, 같은 금지를 여러 번 강조하지 않는다. 긍정문으로 바꾸면서 금지 범위를 넓히거나 의미를 바꾸지 않는다.

채워진 예시 (256자 실측):

```text
매주 금요일 18:00, ~/reports/weekly/의 신규 CSV(헤더 date,team,metric,value)를 팀별 요약표로 변환해 ~/reports/summary.md에 추가하라. 이미 처리한 파일은 건너뛴다(재실행 시 중복 행 0). 파싱 오류 파일은 삭제하지 말고 건너뛴 뒤 ~/logs/weekly.log에 사유를 남긴다. 완료 기준: 처리 파일 수·추가 행 수가 로그에 1줄 기록되고 summary.md 행 수가 로그 누적 수와 일치한다.
```
## 역할 슬롯 — 무엇으로 채우는가

역할은 평가 관점·권한·문체가 결과를 바꿀 때만 쓴다. "최고의 전문가" 같은 지위 장식 대신 필요한 기준이나 산출물 관례를 직접 명시한다.

**프롬프트 단어의 역할 5가지** — 범위 지정(어디서 찾을까?) / 목적 고정(무엇을 달성할까?) / 형식 강제(어떻게 출력할까?) / 오류 금지(무엇을 피할까?) / 행동 지정(어떻게 작업할까?). 각 역할에 맞는 단어를 선택하면 문제 공간이 축소되고 결과가 명확해진다.

**모호어 치환** — 이미 결과가 명확하면 미사여구만 지운다. 모호어가 필요한 요구를 대신하고 있을 때만 관찰 가능한 조건으로 바꾼다. 근거 없는 수량·평가표를 새로 만들지 않는다. 기본 목록은 §모호어 치환을 참고한다.

| 금지어 | 문제점 | 대안 |
|--------|--------|------|
| 대충 | 품질 하한선 붕괴 | 최소 품질 기준·체크리스트 명시 |
| 적당히 | 기대 결과가 불명확할 수 있음 | 주어진 목적에 맞는 기준을 쓰되 수량·길이를 임의로 정하지 않음 |

**역할이 필요할 때만** 대화·증거에서 평가 기준이나 산출물 관례를 고른다. 근거가 없으면 역할을 생략하고 결과를 직접 지시한다. 프레임워크 탐색·기준 열거를 새 과제로 덧붙이지 않는다.

**인물과 프레임워크의 구분** — 인물은 프레임워크의 이름으로만 쓰고, 인물의 목소리로 발화시키지 않는다.
- 금지: `당신은 Michael Porter입니다.`
- 허용: `Five Forces 축(공급자·구매자·대체재·신규진입·기존경쟁)으로 분해하고 각 축의 압력도를 평가하라.`
- 허용: `Porter의 Five Forces 프레임워크를 적용하라.` (관용적 소유격은 명칭이지 귀속이 아니다)

**예시** — 마케팅 전략 수립(214자 실측):

```text
마케팅 컨설턴트처럼 Kotler의 STP 프레임워크(세분화·타겟·포지셔닝)와 Five Forces 모델로 분석하라. 
[입력] 대상 산업·현재 고객군·기존 포지셔닝 
[출력] 세분화 축 3개 > 타겟 고객 프로필 > 포지셔닝 한 문장 > 기존 포지셔닝과의 차이점 3개 
[완료 기준] 각 포지셔닝이 다른 경쟁사와 구분되는 근거를 갖춰야 함. 근거 없는 형용사(혁신적, 독특한) 금지.
```

## 슬롯 자동 채움 — 빈칸은 묻기 전에 채운다

추론 순서는 대화 컨텍스트 → 언급된 저장소·파일 증거 → 아래의 저위험 기본값 → 결과나 하드라인을 바꾸는 빈칸만 질문 ≤3이다. 채운 값은 `가정:` 노트에 남긴다. 결과 자체가 없으면 슬롯 채움이 아니라 요구 구체화 경로다.

| 모드 | 비었을 때 채움 규칙 |
|---|---|
| GOAL | 마지막 언급 프로젝트가 하나로 명확할 때만 대상에 쓰고, 그렇지 않으면 행동 전에 대상을 식별·보고하게 한다. 완료 증거는 관련 테스트·명령 출력으로 둔다. |
| TEAM | 목표·범위는 대화에서 채운다. 독립 검증 표면이 둘 이상일 때만 그 경계에 맞춰 필요한 수의 레인으로 나누고, 검증은 기존 테스트나 측정기로 채운다. |
| CONTRACT | 결과는 대화와 산출물 관례에서 채운다. 완료 기준과 검증이 필요한지는 §CONTRACT를 따르고, 필요한 검증만 실제로 열거나 실행하는 최소 절차로 둔다. |
| BUSINESS | 직무·현실 제약·형식은 대화와 확인된 조직·도메인 관례에서 채우되, 근거 없는 지역·업계 관례는 기본값으로 만들지 않는다. 결과를 가르는 법령·기준 버전은 가정 또는 질문으로 처리한다. |
| MODEL | 대상이 미상이면 특정 모델에 의존하지 않는 목표·입력·핵심 조건으로 쓴다. 형식과 검증은 §MODEL의 포함 조건을 따른다. |
| 리서치 | 출처 유형·확인 날짜·반대 증거는 시점과 결론을 바꿀 때 추가한다. |
| 추출 | 아래 §추출의 소비자 스키마와 결측 규칙을 따른다. |

**추론 불가 슬롯 — 질문이 필요한 기준 (정본)**: 필수 입력이 없거나 충돌해 요청 결과·정확성·권한을 보존할 수 없을 때 묻는다. 대표 사례는 퇴고·델타의 기준 원문, 직접 확인해야 할 원본 자료, 정확한 카피·브랜드명, 실계정·서비스 식별자, 결과를 바꾸는 중요한 방향 선택이다. 나중에 자료를 넣어 실행할 프롬프트를 작성하는 요청이면 입력 위치와 역할을 명시해 완성한다. 지금 그 자료를 읽은 것처럼 말하거나 작성에 불필요한 업로드를 요구하지 않는다.
## 수신자·채널 적응

수신자·채널은 사용자가 지정한 대상과 현재 전달 환경에서 확인한다. 미지정이면 복사 가능한 일반 텍스트로 작성하며 메신저 상한·파일 접근·도구 권한을 가정하지 않는다. 파일·도구 없는 대화 UI에는 필요한 자료를 인라인하고, API 시스템 프롬프트에는 입력 위치·불확실 시 행동을 명시한다. 사람 팀원에게는 사람용 제목·불릿으로 바꾸되 결과·경계·검증은 유지한다. 채널이 달라져도 길이 상한은 전달 채널·타깃 엔진·기계 계약 세 층 중 가장 좁은 것이 구속한다 — 판정 절차와 값의 정본은 [image/surfaces.md](../image/surfaces.md) §0-1이다. 어느 표면이든 다른 파일시스템에는 경로 참조 대신 자기완결로 쓴다.

### 프롬프트 언어 결정

프롬프트 본문의 언어는 아래 순서로 정한다. 요청이 한국어라는 사실만으로 출력 언어를 정하지 않는다 — 비생성형에서는 수신자의 증거이고, 생성형에서는 무관하다.

1. **명시된 출력 언어 지정이 이긴다.** 사용자가 "영어로/한국어로 써줘"라고 하면 그 언어를 쓴다.
2. **재사용·부분 수정은 기준 원문의 언어를 유지한다.**
3. **IMAGE·COMPOSITE·영상 생성 프롬프트는 언제나 영어로 쓴다** — 어떤 생성 엔진이든 동일하다. 화면에 렌더되거나 발화돼야 할 정확 문자열(간판 카피·대사·캡션·제품명·필드값)은 영어 지시문 안에 원어 그대로 둔다. 엔진별 언어 스탬프는 [image/surfaces.md](../image/surface-evidence.md) §7을 따른다.
4. **그 외 프롬프트(CONTRACT·TEAM·GOAL·BUSINESS·MODEL — 작업지시·시스템 프롬프트·자동화·리서치·추출·업무 문서)는 수신자와 작업 컨텍스트의 언어를 쓴다.** 요청·참조 파일·대상 레포의 규칙 문서·납품물이 한국어면 프롬프트도 한국어다. 수신자가 섞여 있거나 불명확하면 요청 언어를 따른다. 수신자가 영어로 일할 때(영어 전용 에이전트·국제 팀·영어 코드베이스와 영어 문서)는 영어다.
5. 어느 경우든 코드·경로·명령·인용문·필드명은 원문 그대로 보존하고, 프롬프트 언어 선택으로 최종 산출물의 언어를 바꾸지 않는다.

이 규칙은 프롬프트의 기본 언어만 정하고 어휘 토큰·정확 문자열은 건드리지 않는다. 로마자 표기 어휘 토큰의 보존은 [references/image/editorial/concept-collision.md](../image/editorial/concept-collision.md)가, 렌더돼야 할 한글의 로마자 변환 금지는 [references/image/typography.md](../image/typography.md) §4가 각각 소유한다.

한국어 수신자용 CONTRACT 예시 (182자 실측):

```text
매주 월요일 09:00에 ~/sales/daily/의 지난주 CSV를 읽어 지점별 매출 합계와 전주 대비 증감률을 표로 정리해 ~/reports/weekly-sales.md에 추가하라. 이미 집계된 주차는 건너뛰고, 누락된 지점 파일은 추정하지 말고 미확인으로 표시한다. 완료하면 처리한 파일 목록과 추가한 행 수를 보고한다.
```

영어 수신자용 CONTRACT 예시 (319자 실측):

```text
Every Monday at 09:00, read last week's CSVs in ~/sales/daily/ and append a per-branch revenue table with week-over-week change to ~/reports/weekly-sales.md. Skip weeks already aggregated, and mark missing branch files as "unverified" instead of estimating. Report the processed file list and added row count when done.
```
## 모호어 치환

| 잘 정리해 | 사용 목적에 맞는 분류·순서를 명시한다. 개수·길이는 요청이나 소비자 계약에 있을 때만 고정한다 |
| 최대한 자세히/빨리 | 필요한 근거·우선순위를 명시한다. 시간 제한은 실제 제약이 있을 때만 쓴다 |
| 필요하면 | 조건 C가 참이면 X로 바꾼다 |
| 등, 기타, 알아서 | 포함 범위나 실행자가 선택할 기준을 분명히 한다. 열린 목록을 임의로 닫지 않는다 |
| 중요한 것 위주로 | 판단 기준을 쓴다 |
| 완벽하게/깔끔하게/고급스럽게 | 판정 가능한 기준과 증거로 바꾼다 |
| nicely / properly / in detail | 영어 표현도 같은 기준으로 필요한 요구를 구체화한다. 인용문·정확 카피는 보존한다 |
## 워크플로우

1. **분류** — 모드 선택. 빈 슬롯은 §슬롯 자동 채움으로 채우고 `가정:`에 기록한다.
2. **결과 명세** — 끝난 상태 1~2문장과 자료 인벤토리. 언급된 경로는 실제로 읽고 사실을 지어내지 않는다.
3. **계약층** — 결과만으로 완료 판정이 불분명할 때 완료 기준을 추가한다. 자율성·게이트·검증·에스컬레이션은 해당 작업에 필요한 것만 붙인다.
4. **구조층** — [prompt-graph.md](../prompt-graph.md) §8의 적용 신호가 있을 때 §3의 조립 절차를 쓴다. 단순하고 충돌 없는 요청은 바로 작성한다. `origin`·`status`는 내부 provenance로만 쓰고, 비자명·비표준 형식에만 채워진 예시 1개를 둔다.
5. **표면층** — 대상 수신자·도구에 맞춘다. 모델 적응·역할 배분이 필요할 때 [model-playbooks.md](../model-playbooks.md)를 읽고, 나머지는 §수신자·채널 적응으로 충분하다.
6. **감량** — 모호어 치환, 제약 모순 해소, 방법 문장 다이어트("지우면 실행자가 틀리는가?").
7. **길이 게이트** — 실측이 필요한 조건·단위·상한은 [image/surfaces.md](../image/surfaces.md) §0-1을 따른다.
8. **드라이런** — 비자명한 형식·실행 계약일 때만 현실 입력과 엣지 사례로 머릿속 실행해 구멍을 수정한 뒤 출력한다.
## 후속 선택

**이 턴이 실제로 프롬프트 블록을 냈고 후속 선택이 유용할 때만** 블록 밖에 평문 `다음:` 메뉴를 붙인다. 검토만 한 턴·스킬 수정·설치·검증 보고에는 붙이지 않는다. 사용자 지정 출력 형식이 메뉴를 허용하지 않거나, 다음 행동을 이미 지시했거나, 사람에게 응답하지 않는 자율 루프 안에서 호출됐거나 기계 핸드오프(S1)이면 생략한다. 사람이 GOAL 프롬프트를 작성해 달라고 한 대화에서도 메뉴가 결과를 부풀리면 생략할 수 있다. 대화형 선택 도구로 응답을 대기시키지 않는다.

1번은 아래 문구로 고정한다.

```text
다음:
1. 자동 개선 — 확인된 결함만 수정하고 의도·범위·조건은 보존
```

**자동 개선은 요청 한 번에 1회만** 수행한다. [SKILL.md](../../SKILL.md) §출력 게이트에서 확인된 결함만 고친다. 모호어를 판정 가능한 조건으로 바꾸고, 저신호 어휘·중복·장식을 줄인다. 목표·범위·권한·모델·구도·소품·조명·컬러 등 결과를 바꾸는 축을 새로 고르지 않는다. 결함이 없으면 `개선할 지점 없음`이라고 알리고 원본을 유지한다. 수정본을 반환한 턴에도 사용자가 후속 선택을 요청했을 때만 메뉴를 붙이며, 사용자가 고르기 전 다음 개선을 자동 실행하지 않는다.

2번 이후에는 **지금 산출물에 적용할 구체적 연산만 최대 3개** 붙인다. 후보는 지정 축의 MODEL-델타, 다른 모델·플랫폼으로 재컴파일, 컷 분리, 레인 전환, 표면 파라미터 조정, 체인의 다음 단계다. 결과가 어떻게 달라지는지 적을 수 없는 `더 자세히`·`다른 스타일로` 같은 항목은 빼며, 후보가 없으면 1번만 둔다.

IMAGE 실행 핸드오프는 [adapters.md](../adapters.md) §이미지 생성 실행 옵션의 조건을 만족할 때 마지막 번호에 붙인다. 실행 도구는 실제 설치와 현재 사용 가능 여부로 판단한다.
## 안티패턴

단계 마이크로매니징(→ 결과와 필요한 완료 조건만 계약) / 장문 인라인 덤프(→ 경로 참조) / 전면 read-only 과잉 차단(→ 좁은 게이트+대체 행동) / 환경 훅이 이미 막는 행동의 이중 게이트(→ 필요성 테스트로 제거) / 질문 반사(→ 추론·기본값 먼저, 질문은 추론 불가 슬롯만) / "알아서" 위임(→ 자율성 3단 경계) / 하나의 비대 goal(→ 분할) / 예시-규칙 충돌 방치(→ 대조 감사) / 무대 지정 어휘("최고 수준으로" → 수치·구체 기준) / 패딩용 문서.
## 보강 루프

결과·모드·레인이 유지되고 한 축만 바뀌면 패치한다. 하나라도 바뀌거나 계약 요소 여러 개가 흔들리면 재작성한다. 압축은 장식 → 중복 → 방법 설명 순으로 줄이며 실제 완료 기준·권한 경계·검증 계약은 보존한다. 실패하면 지시문·입력·도구·환경 중 원인을 먼저 구분한다. 지시문이 원인일 때만 관련 문구를 수정하거나 불필요한 규칙을 삭제한다. 원인이 확인되지 않으면 지시를 늘리지 않는다. 수정 뒤에는 변경한 조건과 그 영향만 대조한다.
