# 텍스트 프롬프트 — 필요한 만큼 구조화하기

이 문서는 구조·빈칸·수신 환경의 판단이 필요한 요청에만 읽는다. 단순 요청은 [SKILL.md](../../SKILL.md)만으로 작성한다. 모드 이름과 아래 항목은 내부 판단 도구이며 출력 양식이 아니다.

## 범용 조립 규칙

먼저 원하는 결과와 실제 입력을 잇는다. 다음 요소는 빠지면 결과가 달라지는 경우에만 덧붙인다.

| 요소 | 필요한 경우 |
|---|---|
| 역할·관점 | 평가 기준·권한·문체가 달라질 때. 지위 장식이나 인물 지명 대신 판정에 쓸 기준을 쓴다(예: 적용 법령·회계기준·표준 문서·사내 규정, 결과를 가르면 버전·시행일까지). 사용자·자료가 정하지 않은 기준은 만들어 넣지 않는다 |
| 완료 기준 | 결과 문장만으로 완료 여부를 판정하기 어려울 때 |
| 출력 형식 | 소비자가 필드·구조·분량을 요구할 때 |
| 절차·도구 | 순서나 도구 선택이 실패를 막을 때 |
| 검증·정지 | 실행·조사·반복 작업에서 무엇을 확인하고 언제 끝낼지가 필요할 때 |
| 이유 | 규칙의 목적이 자명하지 않아 수신자가 경계 사례를 판단해야 할 때. 한 줄로 왜 필요한지 쓴다 |
| 예시 | 분류 경계나 비자명한 출력 형식을 규칙만으로 전달하기 어려울 때 |

피하려는 행동은 금지만 쓰지 말고 대신 할 행동이나 허용 조건을 함께 쓴다(예: "목록 금지" 대신 "병렬 항목이 넷 이상일 때만 목록"). 빈 헤딩은 출력하지 않는다. 예시는 지시와 일치시키고 지시 본문과 구분되게 감싼다. 여러 개를 넣으면 서로 다른 경우를 보여 줘 우연한 공통 패턴을 복제하지 않게 한다. 예시의 수량·도구·평가 수치를 다른 요청에 복사하지 않는다. 필요한 상세 입력은 보존하고 중복 설명만 줄인다. 분량 판단은 [image/surfaces.md](../image/surfaces.md) §0-2를 따른다.

## 기준 원문과 누적 수정

이미지 프롬프트를 포함한 기존 문안의 후속 수정에 적용한다. 이미지 자체의 누적 편집 입력과 프롬프트 문안의 기준 원문은 별개다.

1. **기준 확보:** 사용자가 지정한 원문·첨부 파일을 실제로 읽는다. 같은 대화에서 지정한 기준은 후속 요청에도 유지한다. 한 대화에 여러 문안이 있으면 후속 요청이 가리키는 산출물을 먼저 식별하고, 별도로 납품한 문안은 사용자가 병합을 요청하기 전까지 별도 완성본으로 유지한다. 대상이 여전히 둘로 읽힐 때만 어느 문안인지 짧게 확인한다. 모델이 임의로 축약한 중간본을 새 기준으로 삼지 않는다. 원문을 확인할 수 없으면 접근 가능한 대화·파일부터 찾고, 그래도 없을 때만 요청한다.
2. **변경 범위:** 기준 원문에 사용자가 요청한 변경을 누적한다. “다시 정리해·MPW로 다듬어·전문으로 줘”만으로 헤딩 삭제·문단 병합·전면 요약을 허가받은 것으로 보지 않는다. 명시적인 축약·전면 재작성·형식 전환 요청은 그 범위에서 우선한다.
3. **조립:** 변경을 해당 문장·섹션에 반영하고, 그 밖의 문구·공백·줄바꿈·헤딩 이름·순서·조건·예외는 그대로 복사한다. 새 요구와 직접 충돌하는 기존 문구만 함께 조정한다. 예를 들어 한 부위의 주름 제거를 추가하면 일반 주름 보존 규칙에 그 부위 예외를 반영하되, 조명·피부·프레이밍 항목을 다시 쓰지 않는다. 반영 위치가 애매해도 가장 관련된 기존 섹션에 넣고 무관한 구조는 보존한다. 톤·호칭·문체처럼 전 문장에 걸친 축은 그 축을 표현하는 어휘·어미·호칭만 바꾸고 사실·수량·조건·고유명·정확 문자열·문장 순서는 보존한다. 4단계 대조는 문장 단위 의미 동일성으로 한다.
4. **대조:** 기준 원문과 통합본을 비교해 모든 차이가 요청한 변경 또는 그 변경의 직접적인 충돌 해소인지 확인한다. 이전 턴의 추가 조건도 빠지지 않았는지 확인한다. 긴 원문·여러 차례 수정은 파일 diff 등으로 변경 구간을 확인하고, 의도하지 않은 삭제·축약을 복원한 뒤 납품한다. 읽기 좋은 요약이나 모델 간 동의는 이 대조를 대신하지 않는다.

이 절은 특정 이미지 양식을 모든 요청에 강제하지 않는다. 새 프롬프트는 필요한 구조를 선택하며, 납품 블록과 전문/발췌 구분은 [SKILL.md](../../SKILL.md) §Output format을 따른다.

## 형식이 자주 어긋나는 요청

먼저 충돌하는 기본값·예시를 제거하고, 원하는 결과 형태를 직접 적는다. 예를 들어 한 문장 요청은 한 문장으로 끝나는 지시문을 만들고, 정확한 필드·개수·코드펜스 여부는 실제 답변에서 대조한다. 장황한 금지문이나 “더 잘 따라라”는 반복으로 대신하지 않는다.

- 지시·입력 자료·예시가 섞이면 기존 형식에 맞는 헤딩 또는 태그로 경계를 구분한다. 단순 문장까지 새 태그 체계로 감싸지 않는다.
- 형식 실패가 반복되면 해당 경계를 보여주는 짧은 입력–출력 예시를 넣는다. 예시는 같은 출력 계약을 따라야 하며 예시의 주제·숫자·도구를 실제 요구에 복사하지 않는다. 필요한 개수는 대상 모델의 공식 지침과 실제 평가로 정하고 모든 프롬프트에 고정 개수를 강제하지 않는다.
- 기계 소비 API에 실제 구조화 출력 기능이 있으면 소비자 스키마를 그 기능으로 전달한다. 자연어로 JSON을 요구하는 것, JSON 모드, 스키마 강제는 별개다. 빈 응답·잘림·필드 의미 오류도 따로 검증하며, UI 문안에 API 옵션을 끼워 넣지 않는다.
- 개선 여부는 동일 사례의 원 응답으로 판단한다. 문자·형식 검사를 통과해도 요청 조건의 의미 검토를 생략하지 않는다. 제공사별 적용 근거는 [model-playbooks.md](../model-playbooks.md) §호환 노트를 따른다.

## 쓰기 전에 정할 것

- **결과와 고정 조건:** 대상, 입력 역할, 정확 문구, 수량, 변경·보존 범위, 출력 형식을 먼저 확정한다. 조건이 지금의 프롬프트 답변에 적용되는지, 만들어질 결과물에 적용되는지 구분한다. “다른 설명 없이 프롬프트만”은 이 답변의 부연 제한이며, 이미지 안의 글자·요소를 금지하는 지시로 옮기지 않는다. 이미 있는 조건은 다시 묻지 않는다.
- **창작 가능한 부분:** 사용자가 기획·연출을 맡겼다면 목적에 맞는 구체적 선택을 한다. 지정 축만 고치는 작업에서는 새 스타일·수치·절차를 추가하지 않는다. 창작 선택을 사용자 요구나 확인된 사실로 표현하지 않는다.
- **빈칸과 충돌:** 대화와 제공 자료로 해결하고 결과에 영향 없는 빈칸은 생략한다. 정확성·범위·권한을 바꾸는 미결 사항만 묻는다(아래 §슬롯 자동 채움). 같은 대상의 양립 불가한 필수 조건이 남으면 어느 조건을 유지할지 먼저 묻고, 충돌한 조건을 그대로 묶은 실행 불가능한 완성본은 내지 않는다. 지금 필요하지 않은 자료를 요구하지 않는다.
- **수신 환경:** 접근 가능한 자료와 실제로 주어진 도구만 전제하고, 현재 작성 환경의 도구 목록을 수신자의 도구 목록으로 복사하지 않는다. 이미 제공된 입력은 수신자에게 전달하고 빈 자리표시자로 바꾸지 않는다. 재사용 템플릿을 요청한 경우에만 가변 입력으로 분리하고, 그 입력의 위치와 역할을 표시한다. 이미지 생성·편집 프롬프트의 대상이 미정이면 [surfaces.md](../image/surfaces.md) §0의 기본 작성 경로를 따르고, 그 외 대상 미정 요청은 모델·플랫폼을 임의로 고르지 않는 일반 자연어로 쓴다. 지원 여부가 필요한 문법·필드만 현재 계약에서 확인한다.

## 슬롯 자동 채움 — 질문과 가정

대화 → 제공 자료 → 실제로 필요한 증거 순으로 빈칸을 확인한다. 명시된 경로라도 프롬프트에 위치만 전달하는 작업이면 열 필요가 없다. 파일 내용에 대한 판단이 필요한 경우에만 읽고, 읽지 않은 내용을 확인했다고 말하지 않는다.

**추론 불가 슬롯 — 질문이 필요한 기준 (정본)**: 입력이 없거나 요구가 충돌해 정확성·범위·권한을 보존한 결과를 만들 수 없을 때 묻는다. 예를 들어 부분 수정의 기준 원문, 충돌하는 정확 카피, 실제로 바꿀 계정의 식별자가 해당한다. 나중에 자료를 넣을 재사용 템플릿은 입력 위치와 역할을 표시해 완성한다. 현재 작성에 불필요한 업로드·모델 선정은 요구하지 않는다.

질문은 지금 결정을 바꾸는 것만 묶어 최소화한다. 답과 무관하게 완성할 부분은 진행한다. 중요한 가정만 설명하고, 사소한 표현 선택마다 가정 목록을 붙이지 않는다. 창작을 맡긴 축에는 목적에 맞는 구체적인 안을 제시하되 사실·사용자 요구와 구분한다.

사용자가 이미지 프롬프트 인터뷰를 명시 요청하면 이 최소화 기준 대신 [prompt-interview.md](../image/prompt-interview.md) 절차로 묻는다. 요청이 없으면 이 기준이 정본이다.

## 수신자·채널 적응

수신자가 실제로 볼 수 있는 입력만 참조한다. 다른 기기·파일 없는 대화창으로 옮길 때는 필요한 내용을 포함하거나 사용자가 첨부할 위치를 명시한다. 로컬 경로를 넣었다고 자료가 전달되지는 않는다. 반대로 같은 파일시스템의 실행자에게 자료 전체를 불필요하게 복제하지 않는다.

API 시스템 지시와 요청별 입력이 나뉘면 [contract.md](contract.md)의 메시지 배치를 따른다. 사람 팀원에게 전달할 때는 읽기 쉬운 제목·불릿을 쓸 수 있다. 길이 제한의 적용 순서는 [image/surfaces.md](../image/surfaces.md) §0-1을 따르고, 채널 상한의 실제 값은 수신 환경의 런타임 배선에서 확인한다. 임의의 메신저 상한은 붙이지 않는다.

### 프롬프트 언어 결정

1. 명시된 프롬프트 언어를 따른다.
2. 기존 프롬프트를 재사용·개선·부분 수정하면 원문 언어를 유지한다. 개선을 새 작성으로 취급해 이미지·영상의 영어 기본값으로 번역하지 않는다.
3. 새 이미지·합성·영상 **생성 모델에 직접 넣는** 프롬프트는 영어가 기본이다. 이는 작성 기본값이며 모든 모델에서 영어가 우월하다는 주장이 아니다. 영상·이미지를 만드는 에이전트에게 주는 작업 지시는 4번을 따른다.
4. 그 외에는 수신자와 작업 컨텍스트의 언어를 쓴다. 불명확하면 요청 언어를 따른다.

설명·검토·질문은 대화 언어다. 정확 카피·대사·브랜드명·코드·경로·필드명은 원문을 보존한다. 프롬프트 언어와 만들어질 결과물의 언어는 별개다. 특정 도구의 입력 언어 제약과 명시 요청이 충돌하면 차이를 알리고 필요한 선택만 확인한다.

## 축약어를 활용한 프롬프트 작성

`TL;DR`, `FAQ`, `ELI5`처럼 수신자가 이해할 표현은 사용할 수 있다. `/tone:empathetic` 같은 임의 태그는 공식 명령어나 성능 옵션으로 설명하지 않는다. 태그의 뜻을 따로 길게 정의해야 한다면 자연어가 낫다. 축약으로 입력·보존 조건·출력 요구를 잃지 않는다.

### 사진 연출의 슬래시 키워드

사진 연출을 새로 기획하거나 빠른 스타일 변주를 요청받으면, 목적에 맞는 `/키워드` 조합을 적극적으로 선택해 쓴다. 사용자가 먼저 슬래시를 쓰지 않아도 짧은 연출 입력이 유용한 작업에는 활용한다. 사용자가 보낸 키워드는 변경할 시점·빛·색감·매체 등의 의도로 해석한다. 아래는 선택 예시이며 모든 사진에 붙이는 기본 세트가 아니다.

| 연출 축 | 입력 예시 | 작성할 때 구별할 것 |
|---|---|---|
| 시점 | `/droneview`, `/wormview` | 카메라 위치 변화와 인물의 신체 비율 변경을 구별한다 |
| 렌즈 표현 | `/fisheye` | 가장자리 왜곡의 의도를 읽되, 실제 렌즈 설정을 실행했다고 쓰지 않는다 |
| 조명 | `/nighttimeflash`, `/windowlight` | 광원 방향·배경과의 밝기 관계를 장면에 맞춘다 |
| 화면 구성 | `/flatlay`, `/negativespace` | 카메라 시점과 여백 배치가 기존 크롭·제품 보존 조건에 맞는지 확인한다 |
| 매체 질감 | `/35mmfilmgrain` | [compiler.md](../image/compiler.md) §피부·재질을 따른다 |

**납품 방식:** 조합 자체를 원하면 슬래시 표기를 유지한다. 완성 프롬프트에는 짧은 키워드 조합과 필요한 장면·보존 조건을 함께 쓸 수 있다. 같은 의미를 장문으로 다시 반복하지 않는다. 자연어만 요청했거나 대상이 전용 문법을 요구하면 의도를 그 형식으로 풀어 쓴다. 입력 사진·장면 맥락이 충분하고 사용자가 키워드만 원하면 키워드만 낸다. 출력 형식과 원문 언어는 기존 계약을 따른다.

**선택과 후속 수정:** 시점과 빛처럼 결과를 구별하는 축부터 고르고, 필요한 다른 축만 더한다. 두 개를 의무로 채우거나 상한으로 제한하지 않는다. 명시된 조합이 세 개 이상이어도 개수만으로 삭제하지 않으며, 충돌하는 축만 정리한다. 후속 키워드는 해당 축의 변경으로 반영하고 §기준 원문과 누적 수정에 따라 나머지를 보존한다. 예를 들어 조명 변경에 새 시점이나 피부결을 덧붙이지 않는다. 시점 변경과 원본 구도 고정처럼 양립하지 않는 조건은 임의로 덮지 않는다.

**표면 구분:** 이 표의 `/키워드`는 자연어를 줄인 연출 표기이며 공식 기능 호출·API 필드가 아니다. 실제 호스트 명령이나 프리셋은 현재 도구 계약으로 식별한다. URL·파일 경로·인용 카피의 슬래시는 연출 키워드로 해석하지 않는다. 낯선 키워드는 문맥으로 풀되 결과가 크게 갈리는 의미만 확인한다. 슬래시 자체의 품질 향상이나 얼굴 보존 효과는 검증된 것으로 주장하지 않는다.

참고: [사진 보정 키워드 조합 안내](https://fieldby.notion.site/GPT-159-3f0d730b395381e99f14d5f83a15a458), 2026-10-10 열람. 축별 축약 표기와 조합 방식을 참고한 작성 절차이며 생성 품질 실측은 아니다. 원문의 키워드 개수 권고·반복 재생성 조언을 보편 규칙이나 실행 권한으로 옮기지 않는다.

## 모호어 치환

모호한 표현 자체를 금지하지 않는다. “고급스럽게”가 주어진 자료로 충분히 특정되면 그대로 쓸 수 있다. 결과가 갈릴 때만 목적에 맞는 관찰 가능한 차이로 바꾼다. 수량·점수·기한·도구를 근거 없이 만들어 구체성처럼 보이게 하지 않는다. “알아서”는 위임된 재량일 수 있으며 자동으로 상세 절차나 승인 게이트로 바꾸지 않는다.

## 검토와 보강 루프

기본 검토 기준은 [SKILL.md](../../SKILL.md) §작성과 검수를 따른다. 원문에서 자연스럽게 읽히는 관계를 일부러 모호하게 해석하지 않으며, 정지 이미지의 동작 묘사도 그 자체로 오류가 아니다.

부분 수정은 지정 축의 차이만 남기고 원문을 대조한다. 전면 개선은 현재 목표에 맞게 구조·규칙을 삭제하거나 교체할 수 있다. 실패가 있으면 지시문·입력·도구·환경 중 원인을 먼저 구분한다. 지시가 원인일 때 해당 문구를 고치며, 성능 문제를 금지문 누적으로 해결하려 하지 않는다.

검수는 주장에 맞춘다. 문구 개선은 원문과 비교하고, 기계 산출물은 해당 스키마·검증기로 확인한다. 수신 도구의 실제 파라미터로 따로 전달한 값만 본문에서 생략하며, 전달되지 않는 설정을 빼서 조건을 잃지 않는다. 비교 실험은 요청됐거나 실패 원인 판별에 필요할 때 하고, 원인과 무관한 지시를 계속 덧붙이지 않는다.

### 변경 비교 설계

비교 요청이나 실패 원인 판별에는 실제 사용 입력과 함께 빈 입력·무관한 입력·과도하게 긴 입력·사람도 판정이 갈리는 경계 사례를 준비한다. 정확 일치·스키마·코드 검사로 확인할 수 있는 것은 먼저 기계적으로 대조하고, 주관적 판단에는 점수별 기준이 적힌 루브릭을 쓴다. 독립 판정은 [model-playbooks.md](../model-playbooks.md) §역할·권한 라우팅 5번을 따르며, 결과를 확인하지 않았다면 개선은 가설로 남긴다.

## 답변 형식 세부

본문만·JSON처럼 더 구체적인 지정이 일반 지정보다 우선한다. “결과를 JSON으로 내게 하는 프롬프트”는 수신자의 출력 지시이며, 지금 추출을 실행하거나 MPW 답변을 JSON으로 바꾸라는 뜻이 아니다. 한 문장·정확히 N개처럼 지정한 단위와 수량은 납품 전에 대조한다. 기준 원문을 수정했다면 사용자가 발췌·diff·교체 문단만 요청한 경우 외에는 통합 전문을 내고, “나머지는 동일”이나 교체 지시로 완성본을 대신하지 않는다. 시스템/user 메시지·별도 입력란처럼 수신 환경이 나뉘면 실제 위치를 표시하되 사용자 지정 형식 안에서 구분한다. 설명은 중요한 가정·변경 이유·사용에 필요한 설정만 블록 밖에 짧게 쓰고, ‘프롬프트만’·‘설명 없이’ 요청에는 이 설명도 쓰지 않는다. 검토만 요청하면 검토 결과를, 스킬 관리라면 변경·검증 결과를 보고한다. 완료된 결과 뒤에 후속 메뉴·번호 선택지·추가 작업 제안을 붙이지 않고, 선택을 요구하며 멈추지도 않는다.

## 후속 선택

사용자가 다음 선택을 요청했거나 실제로 남은 결정이 있을 때만 구체적인 선택지를 제시한다. 완성본 뒤에 고정 메뉴·자동 개선 번호를 붙이지 않는다. 후속 실행은 사용자의 요청과 실제 권한에 따라 [adapters.md](../adapters.md)의 해당 경로로 연결한다.
