# 위임 계약 — 실행 작업 공통

실행 위임에서 빠진 조건을 찾을 때 §위임 계약 6요소를 참고한다. 여섯 요소를 모두 출력하거나 별도 양식으로 채울 의무는 없다.

이미 승인된 범위의 되돌릴 수 있는 작업은 진행한다. 보고는 승인 획득이 아니며, 범위·비용·외부 행동의 권한을 새로 부여하지 않는다. 실제 권한·중요한 입력이 빠졌을 때만 그 부분을 질문한다.

**게이트 필요성 테스트** — 금지를 넣기 전 ① 실행자에게 실제로 열려 있는가 ② 환경의 승인 훅·권한이 이미 막지 않는가 ③ 이 범위에서 실제로 발생 가능한가를 확인한다. 하나라도 아니오면 중복 게이트를 만들지 않는다. 기존 사용자 경계는 보존하고, 허용된 로컬 작업의 검증은 위험에 맞춰 diff·백업·dry-run 중 필요한 것을 쓴다.

## 위임 계약 6요소

실행 작업을 위임할 때 아래를 점검하되, 결과를 바꾸는 요소만 문장에 남긴다. 단순 즉시 응답에 별도 승인·중단·검증 절차를 억지로 넣지 않는다.

| 요소 | 계약이 답해야 할 질문 |
|---|---|
| 결과 명세 | 끝난 상태는 무엇인가? |
| Definition of Done | 무엇을 보면 완료라고 판정하는가? |
| 결정권 | 실행자가 정할 것과 사용자 판단·승인이 필요한 것은 무엇인가? |
| 하드라인 | 범위에서 실제로 지켜야 할 경계는 무엇인가? |
| 검증 계약 | 완료 전에 확인할 결과는 무엇이고, 보고에 어떤 증거(실행 명령과 실제 출력·파일 경로)를 붙이며, 확인하지 못한 항목과 실패한 검사를 어떻게 구분해 적는가? |
| 에스컬레이션 | 해결을 시도해도 남는 막힘을 언제, 어떻게 보고하는가? |

이미 허가된 실행 범위에서는 필요한 구현·동작 확인·문제 수정을 끝낸 상태를 완료로 정한다. 실제 승인 경계가 없으면 첫 구현 뒤 검토 대기를 기본 종료점으로 넣지 않는다.

## 도메인별 추가 조건

- 코딩 작업에는 기존 패턴과 테스트, 수정 범위, 무관한 변경의 배제 중 실제 결과를 가르는 것만 적는다. 작업 중 찾은 별도 결함이나 성능 문제는 이번 동작에 필요하지 않으면 후속 과제로 보고한다. 요구가 모호하면 문언과 주변 코드가 가장 직접 지지하는 해석을 구현하고 가정을 밝힌다. 도구를 쓰는 실행자에게는 수신자의 실제 도구 정의를 알 때만 실제 호출 예시 1개를 넣는다. 수정 후에는 테스트와 파일의 적용 결과를 확인한다. 리뷰라면 발견을 신뢰도·심각도와 함께 모은 뒤 소비자 쪽에서 필터링한다.
- 에이전트 작업에는 허가된 하위 작업을 끝내는 기준과 완료 증거를 둔다. 독립 읽기의 병렬화와 빈 결과의 다른 조회는 실행 환경이 허용할 때 적용한다. 도구 호출 설명은 중요한 전환점에 맞추고, 필요하면 [model-playbooks.md](../model-playbooks.md) §호환 노트의 dated note에 따라 진행 보고를 조정한다. 여러 단계의 상태는 작업표로 추적하며 긴 작업의 문맥 처리는 [model-playbooks.md](../model-playbooks.md) §컨텍스트 운용을 따른다. 검증은 변경 규모와 필수 검사에 맞추고 통과 후에는 새 실패나 열린 우려가 있을 때만 넓힌다.
